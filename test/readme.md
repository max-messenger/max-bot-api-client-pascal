Add some data so that you can test the MAX bot API wrapper. The tests read them from the file `testmax.ini` in the working directory of the test
``` INI

[Bot]
;; Please specify bot token below!
Token=

[API]
;; Optional: custom API endpoint (overrides the built-in MaxAPI_URL)
;; Endpoint=
[Chat]
;; Enter Your user/chat ID
ID=

[User]
;; Optional: user ID (read into TTestMaxClass.UserID, no test asserts it yet)
ID=

[Send]
;; Https URL for the setWebhook / deleteWebhook tests
url=
;; Url of an already uploaded photo (for the sendPhoto test)
photourl=
;; Photo filename for the sendPhotoByFileName / uploadFile tests
PhotoFile=

;; The proxy is configured through the TMaxSender properties HTTPProxyHost/HTTPProxyPort/HTTPProxyUser/HTTPProxyPassword (both brokers).
;; The keys below are not read from the INI by the tests.
[Proxy]
Host=
Port=
Username=
Password=
Uri=
;;Uri=username:password@host:port
```

- `TTestWebhookScan` - offline tests of the webhook body depth scanner (`JSONBodyTooDeep` of the `maxwebhook` unit; the scanner moved here from the `webhookutils` unit of the `examples/Webhook` example): an empty body and a real update pass, exactly the 64-level limit passes while 65 levels is rejected, brackets inside string literals stay data (escaped quote, double backslash, unterminated string) and closers before openers neither hide nor discount the depth;
- `TTestMultipartBody` - offline tests of the `TMaxMultipartStream` composite (the UploadFile body is streamed from the source file instead of being buffered whole, td-048): the composite bytes match the stock multipart layout byte for byte, the Size is exact before the first Read (it feeds Content-Length), a rewind-and-reread is byte-identical (the keep-alive loop seeks the body back before every send attempt), 3-byte chunked reads concatenate into the same body, and a nil or empty form-field list yields the file part only;
- `TTestMultipartBoundary` - offline end-to-end tests of the broker multipart boundary (td-077/td-096), both brokers through the registered HTTP client against the local loopback sink `TTestMultipartSink` (a plain fphttpserver capture on 127.0.0.1 holding each request's Content-Type and body): the boundary in the body framing is the boundary of the Content-Type header, two sequential calls produce different boundaries - the second upload carries the REAL boundary of the first call in its file bytes (the td-077 crafted-file shape) and still goes out, so the boundary is fresh per call - and a file holding a captured boundary passes the buffered `FilesFormPost` collision gate without a false positive (the gate rejects the current call's boundary only; a regression to pattern matching or to a whole-body scan - whose framing holds the boundary by design - turns this red). The collision raise itself (a file holding the CURRENT call's boundary) stays untestable through the public API: the boundary is fresh per call and observable nowhere before the gate on both brokers, and the brokers must not grow test-only surface (td-096);
- `TTestStringBody` - offline tests of the `TMaxStringBodyStream` wrapper (the ApiCall JSON body is served straight from the referenced string buffer instead of being copied into a `TStringStream`, td-048): the Size is exact before the first Read (it feeds Content-Length), a rewind-and-reread is byte-identical (a keep-alive retry replays the same bytes), reads shorter than the remaining body concatenate into the same body, a seek outside the body or an unsupported seek origin fails loudly, and an empty string yields Size=0 and a zero-byte Read; the same suite pins the compact serialization the stream serves (`JSONCompact`): no padding byte for byte, the escaping of values and keys, raw UTF-8 stays raw, finite scalars delegate to their own AsJSON form while a NaN/Infinity float raises, the compact body round-trips semantically, and a nil tree yields the empty body;
- `TTestWebhookReceiver` - offline end-to-end tests of `TMaxWebhookReceiver` (the `maxwebhook` unit); every test drives a real receiver on `127.0.0.1` through the registered HTTP client, loopback only: a valid delivery is answered 200 `{}` and reaches `OnUpdate` (type, chat id, text), a wrong secret gets 403 with an empty body and never reaches `OnUpdate`, the matching secret delivers, an oversized body and a too-deep body are answered 200 with a warning and no delivery, a non-JSON body gets 200 with an error logged from the generic handler except-block, the td-083 log-forging guard is pinned by `ParseErrorLogEscapesControlBytes` (a malformed body whose invalid string token decodes to raw control bytes still gets 200 while its logged `request failed` line carries the token only in the escaped `\xNN` form - no raw control byte survives into the captured log), a JSON non-object gets 200 with a warning, an empty body gets 200 silently, a bind conflict raises `EMaxConfig` naming the port with the original bind error kept, and a TLS delivery over the self-signed fixture pair in `test/certs/` (the client disables certificate verification) is answered 200 - the last one needs a loadable classic OpenSSL library on the host. The TLS deadline contract (td-082) is pinned by `TLSTruncatedRequestHitsDeadline`: a raw TLS client (not the registered broker) sends a request head promising a body it never finishes, the receiver shortened through the protected `ConnectionIOTimeoutMs` property cuts the connection at the deadline, the expiry surfaces as an `etError` log line, no delivery is processed and no answer goes out, while a full request straight after still delivers and answers 200; the same test needs the loadable classic OpenSSL library. The td-101 twin of the log-forging pin is `ConnectionLogWarningEscapesControlBytes`: the test subclass `TLogExposeReceiver` exposes the protected `HandleServerLog` seam and feeds it the exact message shape of the setsockopt degradation warning call site (`'IO deadline not set on a connection: ' + E.Message`, the socket-error text is peer-controlled), the control bytes of the forged message reach the captured log only in the escaped `\xNN` form, and the pin is deterministic - the receiver is only constructed, never started, so there is no transport race in it;
- `TTestFCLBrokerDefaults` - offline tripwire of the broker constructor defaults (td-111): a direct `Create(nil)` of the broker class asserts `SSLVerifyCert=True` and `SSLCAFile=''` right after the constructor, no network. The tripwire bypasses the registry - the `TBaseHTTPClient` broker-class registry is single-slot (a second registration over an occupied slot raises `HTTP client class already registered!`; with two linked broker units the displacement still comes out last-wins, because each broker unit's initialization calls `UnregisterClientClass` before its own registration), so a constructor default is observable only by instantiating the class itself - and the `TMaxSender` path is deliberately bypassed: its private `CreateHTTPClient` overwrites the fresh client with the configuration copy (`Result.SSLVerifyCert:=AConfig.VerifyCert`), so through a sender the test would observe the configured value, never the constructor default. A future broker unit without `FSSLVerifyCert:=True` in its constructor would silently turn server-certificate verification off for every direct consumer of the broker class (code that instantiates the registered client itself); senders are immune (their `CreateHTTPClient` overwrites the constructor default with the configuration copy and the `TMaxSender` default keeps verification on) - this pin turns that regression red instead of leaving it to discipline;
- `TTestSenderProcedure.sendMessage` - sends a message through the standalone `TMaxBotSendMessage` function;
- `TTestSender` - the object style tests against a real bot: `getMe`, `sendMessage`, `sendMessageWithInlineKeyboard`, `sendPhoto` (by URL), `sendPhotoByFileName` (two-step upload), `uploadFile`, `setWebhook`, `deleteWebhook`, `ReceiveUpdate` (long polling).

In order to test receiving updates via longpolling (`TTestSender.ReceiveUpdate`), send a message or other \[action\] to the bot just before running the test.

Building the console test runner against the `bot_ex` units (`TTestMaxBot` needs them). Run the commands from the repository root - all the paths below are relative to it:

``` bash
mkdir -p test/lib
fpc -B -dni18n -dUseCThreads -Futest -Fubot_ex -Fu. -Fuexamples/daemon -FEtest -FUtest/lib test/console.lpr
test/console --format=plain --all
```

`-FUtest/lib` keeps the compiled `.ppu`/`.o` files out of `test/`, where they could shadow the ppu of the package on the next IDE build. `-dUseCThreads` is required on Linux and macOS alike: the receiver tests create real threads, and without `cthreads` the build is green but the first thread crashes at runtime (error 232).

Without a filled `testmax.ini` (the tests need network and TLS) `--all` normally reports 10 red tests: 9 failures in `TTestSender` and 1 error in `TTestSenderProcedure.sendMessage` - a TLS/setup failure whose message depends on the host's OpenSSL (`Could not initialize OpenSSL library` where FCL-SSL cannot load OpenSSL, `Fail to send message from bot!` where it can) - this is not a broken build. On a host where the classic OpenSSL library does not load, both TLS delivery tests of `TTestWebhookReceiver` - `TLSDeliversUpdate` and `TLSTruncatedRequestHitsDeadline` - add one more such error each, failing with the same `Could not initialize OpenSSL library` (see the suite bullet above). The 114 offline tests are checked by the eleven offline suites, one suite per run (a repeated `--suite` replaces the previous one):

``` bash
test/console --format=plain --suite=TTestSenderTypes
test/console --format=plain --suite=TTestMaxBot
test/console --format=plain --suite=TTestDesignTime
test/console --format=plain --suite=TTestDaemonStartFailure
test/console --format=plain --suite=TTestTLSTrust
test/console --format=plain --suite=TTestWebhookScan
test/console --format=plain --suite=TTestMultipartBody
test/console --format=plain --suite=TTestMultipartBoundary
test/console --format=plain --suite=TTestStringBody
test/console --format=plain --suite=TTestWebhookReceiver
test/console --format=plain --suite=TTestFCLBrokerDefaults
```

CI runs the offline suites through an explicit list (`.github/workflows/make.yml` -> `.github/workflows/make.pas test`, the Linux leg) - the list is the block above verbatim - and `--all` stays out of CI because the live-token suites fail without a filled `testmax.ini` (environmental red, not a regression).

`-dni18n` defines the symbol `ni18n`, which excludes the Lazarus `Translations` unit (see `bot_ex/maxbot.pas`), so it is required unless that unit is on the search path.
